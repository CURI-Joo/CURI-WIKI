# CURI Wiki Guide

> CURI Wiki는 CURI 팀의 제품 지식, 작업 기준, 운영 문서, 의사결정 기록을 한 곳에 모아 함께 관리하기 위한 내부 Wiki입니다.

## Why Wiki?

업무 정보가 개인 메모, Telegram, 구두 공유, 흩어진 파일에만 남아 있으면 시간이 지나면서 다시 찾기 어려워집니다.

- 어디에 최신 정보가 있는지 알기 어렵습니다.
- 새 팀원이 같은 설명을 반복해서 들어야 합니다.
- 이전에 왜 그렇게 결정했는지 확인하기 어렵습니다.
- 제품, 운영, 디자인, 개발 기준이 사람마다 다르게 이해될 수 있습니다.

CURI Wiki는 팀에서 계속 참고해야 하는 정보를 문서로 남기고, 필요한 사람이 빠르게 찾을 수 있도록 돕습니다.

## Structure

CURI Wiki의 기본 구조는 `HOME → Category → Document`입니다.

```text
HOME
├─ CURI AI
├─ ETC
└─ WAME
```

문서를 작성할 때는 가장 관련 있는 카테고리에 넣습니다. CURI AI나 WAME처럼 제품이 명확하면 해당 카테고리를 선택하고, 공통 안내나 기타 문서는 ETC에 작성합니다.

## Wiki에 남기면 좋은 정보

Wiki에는 팀원이 반복해서 확인해야 하는 정보를 남깁니다.

| 종류 | 예시 |
| --- | --- |
| 제품 지식 | 기능 설명, 사용자 흐름, 주요 정책 |
| 작업 기준 | 디자인 기준, 개발 컨벤션, QA 기준 |
| 운영 정보 | 계정 관리, 배포 전 체크리스트, 장애 대응 방법 |
| 온보딩 자료 | 신규 팀원이 처음 알아야 할 제품/업무 정보 |
| 의사결정 기록 | 결정 배경, 선택한 방향, 참고한 자료 |

단기 대화나 바로 처리할 문제는 Telegram에서 공유할 수 있지만, 나중에 다시 찾아야 하는 내용은 Wiki에 정리합니다.

## 문서 찾는 방법

1. **HOME**에서 관련 카테고리를 선택합니다.
2. 문서 목록에서 제목과 요약을 확인합니다.
3. 찾는 문서가 보이지 않으면 검색을 사용합니다.
4. 문서를 열어 본문, 작성자, 마지막 수정일을 확인합니다.

문서를 찾을 때는 정확한 제목을 몰라도 제품명, 기능명, 키워드로 검색하면 됩니다.

## 문서 작성 화면

Wiki 글 작성 화면에서는 아래 항목을 순서대로 입력합니다.

| 항목 | 선택 또는 입력값 | 설명 |
| --- | --- | --- |
| **카테고리** | CURI AI / ETC / WAME | 글이 저장될 위치입니다. |
| **작성 방식** | 일반 글 / Markdown | 글을 어떤 방식으로 작성할지 선택합니다. |
| **제목** | 직접 입력 | 목록과 검색 결과에 보이는 문서 이름입니다. |
| **내용** | 직접 입력 | 팀원이 실제로 참고할 본문입니다. |
| **저장** | 버튼 클릭 | 입력한 내용을 Wiki에 저장합니다. |

## 카테고리 선택

| 카테고리 | 사용 기준 |
| --- | --- |
| **CURI AI** | CURI AI 제품, 기능, 운영, 정책과 직접 관련된 글 |
| **ETC** | 여러 제품에 공통으로 적용되거나 분류가 애매한 글 |
| **WAME** | WAME 제품, 기능, 운영, 정책과 직접 관련된 글 |

카테고리가 애매하다면 우선 ETC에 작성합니다. 이후 팀에서 더 적절한 위치가 정해지면 카테고리를 변경하면 됩니다.

## 작성 방식 선택

| 작성 방식 | 사용 기준 |
| --- | --- |
| **일반 글** | 짧은 안내, 간단한 메모, 빠르게 공유해야 하는 내용을 작성할 때 |
| **Markdown** | 제목, 목록, 표, 코드 블록, 체크리스트처럼 구조가 필요한 글을 작성할 때 |

사내 가이드, 운영 절차, 체크리스트처럼 나중에 다시 읽을 문서는 Markdown으로 작성하는 것이 좋습니다.

## 문서 작성 방법

1. HOME 또는 문서 목록에서 **새 문서**를 클릭합니다.
2. **카테고리**에서 CURI AI, ETC, WAME 중 하나를 선택합니다.
3. **작성 방식**에서 일반 글 또는 Markdown을 선택합니다.
4. **제목**을 입력합니다.
5. **내용**을 작성합니다.
6. **저장** 버튼을 클릭합니다.

문서 제목은 나중에 검색하기 쉽도록 구체적으로 작성합니다.

- 권장: `CURI Wiki Issue Guide`
- 권장: `Admin 배포 전 체크리스트`
- 권장하지 않음: `정리`, `참고`, `회의 내용`

## 문서 상태

문서는 상태에 따라 작성 단계와 사용 가능 여부를 구분합니다.

| 상태 | 의미 |
| --- | --- |
| **Draft** | 작성 중인 문서입니다. 내용이 아직 확정되지 않았습니다. |
| **Published** | 팀원이 참고해도 되는 문서입니다. |
| **Archived** | 더 이상 사용하지 않거나 이전 기록으로만 남긴 문서입니다. |

팀에서 바로 참고해야 하는 문서는 Published 상태로 관리합니다. 오래되었거나 더 이상 맞지 않는 문서는 삭제하기보다 Archived로 남겨두는 것이 좋습니다.

## 공개 범위

문서는 기본적으로 회사 내부 공개를 기준으로 작성합니다.

| 공개 범위 | 의미 |
| --- | --- |
| **COMPANY** | CURI 팀원이 볼 수 있는 문서입니다. |
| **RESTRICTED** | 지정된 팀원만 볼 수 있는 문서입니다. |

계정, 계약, 민감한 운영 정보처럼 접근 제한이 필요한 내용은 RESTRICTED로 작성합니다.

## 좋은 Wiki 문서 작성 기준

좋은 Wiki 문서는 길이보다 다시 읽었을 때 바로 쓸 수 있는지가 중요합니다.

- 첫 문단에서 문서의 목적을 설명합니다.
- 필요한 사람이 바로 따라 할 수 있도록 순서대로 적습니다.
- 결정 사항과 참고 정보를 구분합니다.
- 표, 목록, 예시를 사용해 빠르게 읽을 수 있게 합니다.
- 오래된 내용은 수정하거나 Archived 상태로 변경합니다.
- 문서가 길어지면 섹션을 나누고 제목을 명확히 씁니다.

## ISSUE와 Wiki의 차이

ISSUE와 Wiki는 목적이 다릅니다.

| 구분 | 목적 | 예시 |
| --- | --- | --- |
| **ISSUE** | 문제와 개선사항을 등록하고 해결 상태를 추적 | 버그, UI 오류, 기능 개선 요청 |
| **Wiki** | 팀이 계속 참고할 지식과 기준을 정리 | 사용 가이드, 운영 절차, 제품 정책 |

문제가 발생했고 해결이 필요하다면 ISSUE에 등록합니다. 해결 방법이나 반복해서 참고할 기준이 생겼다면 Wiki 문서로 정리합니다.

## 추천 작성 흐름

```text
1. 공유해야 할 정보가 생김
2. 일회성 대화인지, 계속 참고할 정보인지 판단
3. 계속 참고할 정보라면 Wiki 문서 작성
4. 카테고리 선택 (CURI AI / ETC / WAME)
5. 작성 방식 선택 (일반 글 / Markdown)
6. 제목 입력
7. 내용 작성
8. 저장
9. 내용이 바뀌면 문서 업데이트
```

## 작성 예시

```text
카테고리: CURI AI
작성 방식: Markdown
제목: CURI AI 설문 결과 확인 가이드

본문:
- 어떤 상황에서 보는 문서인지
- 어디로 접속해야 하는지
- 어떤 값을 확인해야 하는지
- 자주 발생하는 예외 상황은 무엇인지
- 문제가 있을 때 누구에게 공유해야 하는지
```

## FAQ

**Q. 어떤 내용을 Wiki에 써야 할지 모르겠어요.**  
A. 다른 팀원이 나중에 다시 물어볼 가능성이 있는 내용이면 Wiki에 남기는 것이 좋습니다.

**Q. 문서를 잘못 작성했어요.**  
A. 내용을 수정하거나 상태를 Draft 또는 Archived로 변경하면 됩니다.

**Q. 카테고리가 애매해요.**  
A. 우선 가장 가까운 카테고리에 작성하고, 정말 애매하면 ETC에 작성합니다.

**Q. Telegram에 공유한 내용도 Wiki에 다시 써야 하나요?**  
A. 계속 참고해야 하는 결정, 절차, 기준이라면 Wiki에 정리해두는 것이 좋습니다.
